# Булшитометр

Разбирает публичные тексты автора (посты, анонсы, ответы, расшифровки)
и показывает, как в них устроены давление, обещания, эксклюзивность
и коммерция, а рядом проверяемость, добросовестность и автономия.
Результат: тип из семи, уверенность, семь осей словами, найденные
цитаты с объяснением и альтернативной трактовкой.

Модель только размечает цитаты. Всё остальное, от баллов до типа,
считает код по таблице из рубрики доменного пакета, `packs/courses/rubric.json`.

## Запуск

```
npm install
npm test                  # node --test, сеть не нужна
npx netlify dev           # страница и функции локально
```

Для `netlify dev` нужен `ANTHROPIC_API_KEY` в окружении, остальные
переменные имеют значения по умолчанию.

### Переменные окружения

| Переменная | Что это | По умолчанию |
|---|---|---|
| `ANTHROPIC_API_KEY` | ключ Claude API, только на сервере | обязателен |
| `IP_SALT` | соль для хеша IP и подписи заданий фоновой функции | обязателен |
| `DAILY_CAP` | сколько вызовов модели в сутки на весь сайт; на время теста 50–100 | 500 |
| `HOURLY_PER_IP` | сколько разборов в час с одного адреса | 10 |
| `MODEL_EFFORT` | глубина размышления модели: `low`…`max` | `medium` |

`ANTHROPIC_API_KEY` и `IP_SALT` помечаются в Netlify как секреты.
Без любого из них функции отвечают 500 и в сеть не ходят.

Ключ API выпускается в Claude Console, счёт там же. Подписка Claude
(Pro, Max) к сайту не подключается: сайт ходит в модель сам, без
человека, и платит по объёму. Кроме `DAILY_CAP` стоит поставить
месячный потолок расходов в Console.

### Ошибки модели в логе и на странице

| Что случилось | Лог функции `analyze-background` | Человек видит |
|---|---|---|
| Кончился баланс (402 или 400 про credit balance) | `error=billing:402` | «Разборы на паузе: у сервиса кончился баланс» |
| Неверный или отозванный ключ (401) | `error=auth:401` | «Что-то сломалось на нашей стороне» |
| Перегрузка, 429, 5xx: один повтор через 2 с | `error=overloaded_error:529` | «Модель занята, попробуй через минуту» |
| Дневной лимит `DAILY_CAP` | `error=budget` | «Перерыв на кофе…» |

Баланс и ключ повтором не чинятся, поэтому повтора у них нет.
Ключ не попадает ни в страницу, ни в ответы, ни в логи, даже внутри
текста чужой ошибки: `engine/app.mjs` вычищает его перед выдачей.

## Как устроен разбор

```
страница ──POST /api/analyze──▶ лимиты → кэш ──HIT──▶ 200 с результатом
                                         └─MISS─▶ бюджет → задание → 202 {job}
         ◀──GET /api/analyze?job=… раз в 2 с──  202 пока идёт, потом 200
фоновая функция: разметка моделью → проверка цитат → запись в кэш
```

Синхронная функция Netlify живёт около 10 секунд, а разметке с
размышлением модели нужно больше. Поэтому разметка идёт в фоновой
функции `analyze-background` (до 15 минут), а страница опрашивает
задание. **Фоновые функции есть не на всех тарифах Netlify**: перед
запуском проверьте, что на тарифе сайта они включены, иначе каждый
разбор закончится ошибкой 502.

Порядок проверок в `/api/analyze` и есть защита денег: метод, Origin,
размер тела, форма входа, частота с адреса, кэш, дневной бюджет.
До модели доходит только то, что прошло всё.

Хранилище: Netlify Blobs, четыре стора (`extractions`, `ratelimit`,
`counters`, `jobs`). В кэш пишется разметка: короткие цитаты, сигналы,
пояснения и число слов по текстам. Сами тексты не хранятся нигде.
Кэш живёт 30 дней. Счётчики в Blobs не атомарны: при одновременных
запросах лимит может пропустить лишний вызов, для MVP это приемлемо.

## Как считается результат

Формулы и все числа лежат в `packs/courses/rubric.json`, код в `engine/score.mjs`
только их применяет.

1. **Балл находки:** `c = w · m_strength · Π m_modifier · m_genre`.
   `w` вес сигнала, сила 1–3 даёт множитель 0.5 / 1 / 1.5, модификаторы
   (гарантия, срок, условие, конкретность) умножают дальше, а жанр
   «продажа» ослабляет дедлайн, дефицит и ступени: в анонсе они
   ожидаемы.
2. **Насыщение по тексту:** `S = sign(w) · min(Σ|c_k| / k, 3·|w|)`.
   Десять одинаковых приёмов в одном тексте не весят в десять раз больше.
3. **Шаблонные тексты:** тексты с похожестью по словесным 5-граммам
   от 0.8 или помеченные моделью как шаблон склеиваются в один кластер.
   Сто одинаковых постов считаются как один.
4. **Ось:** `raw = m_scenario · (1 / n_eff) · Σ S`, где `n_eff` число
   кластеров, а `m_scenario` усиливает важное для сценария (курс,
   терапевт, учитель, реклама). Затем `v = 1 − e^(−raw / k)` и уровень:
   ниже 0.25 низкий, до 0.6 средний, выше высокий.
5. **Уверенность:** низкая при меньше чем 3 разных текстах или 800
   словах; высокая от 8 разных текстов, 3000 слов и не больше 60 %
   продающих; иначе средняя. Если больше 30 % цитат модели не нашлось
   в текстах дословно, уверенность падает на ступень.
6. **Тип:** первое сработавшее правило из `types` в рубрике. Низкая
   уверенность всегда даёт «Тёмную материю».

Цитата, которой нет в тексте после нормализации (регистр, ё, кавычки,
тире, пробелы), отбрасывается до подсчёта. Модель не может добавить
балл за то, чего автор не писал.

**Веса экспертные, версия 1.** Их никто не мерил на размеченной
выборке. Это договорённость о том, что считать сильнее, а не
измеренная истина, и страница в блоке «Честный язык» так и говорит.
Любая правка весов меняет `version` в рубрике.

## Модель

`claude-sonnet-5` через `fetch`, без SDK. Инструмент `report_findings`
принудительный и строгий: ответ всегда валиден по схеме. Размышление
адаптивное, глубина из `MODEL_EFFORT`.

`temperature: 0` не отправляется: у этой модели параметры сэмплинга
убраны, и любое значение кроме умолчания даёт 400. Одинаковый ответ
на одинаковый вход держат кэш разметки и подсчёт в коде.

Переход на более дешёвую модель, например Haiku 4.5, это не замена
одного имени: у моделей до поколения 4.6 другая схема размышления
(`budget_tokens` вместо `adaptive` и `effort`), запрос придётся
собирать по-другому. Сравнивать качество тем же `eval.mjs`.

Промпт в `packs/courses/prompt.md`, первая строка `prompt-version: N`.
Версия промпта входит в ключ кэша: новая версия промпта сама
сбрасывает кэш.

## Вопросы и ответы

На входе человек отмечает, что хочет понять до оплаты: семь вопросов,
три выбраны по умолчанию. Выбор уходит в `POST /api/analyze` полем
`questions` (массив id в порядке выбора). В ключ кэша он не входит:
от него зависит только порядок вопросов продавцу.

Ответы строит `engine/answers.mjs` поверх уже посчитанного результата.
Модель в этом не участвует, веса и пороги не меняются. Тексты вопросов,
шаблонов и вопросов продавцу лежат в `rubric.questions` и
`rubric.seller_fallback` пакета, вступление сообщения в
`copy.json` пакета (`result.seller_intro`).

Откуда берётся каждый ответ:

| Вопрос | Источник | Подтверждения |
|---|---|---|
| `q_now` Почему решать нужно сегодня? | уровень оси Давление | находки Давления |
| `q_promise` Что мне на самом деле обещают? | уровень оси Обещания | находки Обещаний |
| `q_fit` Сработает ли это для меня? | уровень оси Добросовестность | средний и высокий: находки с плюсом; низкий: с минусом |
| `q_check` Можно ли это проверить заранее? | уровень оси Проверяемость | так же |
| `q_cost` Сколько это будет стоить в итоге? | уровень оси Коммерция | находки Коммерции |
| `q_after` Смогу ли я потом без него? | уровень оси Автономия; при высокой Эксклюзивности шаблон «зависимость» | находки Автономии или Эксклюзивности |
| `q_fail` Что будет, если не получится? | сигналы: `unfalsifiable`, `shame_doubt`, `hidden_terms`, иначе `negative_case`, иначе «молчание» | находки этих сигналов |

Правила:

- шаблон выбирается по уровню оси; если уровень выше нижнего, а
  подходящих находок нет, берётся нижний шаблон;
- `{n}` в шаблоне это число подтверждений, `evidence` это три самых
  весомых из них, ссылками `f<i>` на `findings[i]` того же ответа;
- при низкой уверенности у всех ответов `preliminary: true`;
- вопросы продавцу: сначала от выбранных вопросов, потом от остальных,
  внутри по тревожности, без повторов, не больше пяти; если меньше трёх,
  добиваются общими из `seller_fallback`;
- `in_favor`: до трёх находок Проверяемости, Добросовестности и
  Автономии с плюсом.

Страница ничего не пересчитывает: она ставит выбранные ответы наверх
в порядке выбора, остальные сворачивает в «Ещё мы заметили». Список
вопросов для переключателей страница берёт из `/api/pack`.

События: `answer_open` (раскрыты цитаты ответа или свёрнутый ответ) и
`seller_questions_copied`, каждое не чаще раза на разбор.

## Доменные пакеты

Движок один, домен это папка с данными в `packs/<id>/`. Сейчас пакет
один, `courses`. Страница и API выбирают пакет по id: `?domain=` в
адресе страницы и поле `domain` в `POST /api/analyze`. Без него берётся
`courses`, неизвестный id даёт 400. Публичную часть пакета (тексты,
сценарии, жанры, вопросы, без весов и промпта) отдаёт
`GET /api/pack?domain=…`.

### Как добавить домен

Создать папку `packs/<id>/`, где `<id>` это строчные латинские буквы,
цифры и дефис, и положить в неё четыре файла. Кода в пакете нет.

| Файл | Что в нём |
|---|---|
| `pack.json` | `id` (равен имени папки), `version`, `title`, `language`, `evidence.kind` (сейчас только `quote`), `genres` (порядок жанров в интерфейсе, первый по умолчанию), `scenarios` (id, подпись, ровно один `default`) |
| `rubric.json` | оси, сигналы с весами, жанры, сценарии, пороги, уверенность, счётчики карточки, правила типов, вопросы с шаблонами, общие вопросы продавцу |
| `prompt.md` | промпт разметки; первая строка `prompt-version: N`, в тексте место `{{SIGNALS}}` |
| `copy.json` | строки интерфейса про домен: вход, блоки результата, названия и строки типов, адвокат, «Чего мы не знаем», подписи счётчиков карточки |

Обязательные ключи `copy.json` перечислены в `REQUIRED_COPY` в
`engine/packs.mjs`: это контракт пакета.

Загрузка проверяет и отказывает с текстом «пакет, файл, ключ»:

- `id` совпадает с папкой, вид подкрепления поддерживается движком;
- id сценариев совпадают с `rubric.scenario`, жанры в `pack.json` с
  `rubric.genres`;
- у каждого сигнала есть ось, оси и сигналы в правилах типов,
  вопросах, жанровых и сценарных множителях и счётчиках существуют;
- последний тип срабатывает всегда, у вопросов по оси есть шаблоны
  уровней 0, 1, 2, условия встречного вопроса ссылаются на шаблоны;
- в `copy.json` есть все обязательные ключи, строки для каждого типа
  рубрики и только для них, счётчики карточки есть в `rubric.counts`;
- промпт начинается с версии и содержит `{{SIGNALS}}`.

Пакет по умолчанию грузится на холодном старте функции: сломанный
пакет роняет её сразу, с ошибкой в логе. Любая правка рубрики, промпта
или текстов пакета поднимает `version` в `pack.json`; id пакета и
версия промпта входят в ключ кэша разметки.

Если для нового домена в движке понадобился бы `if` по id пакета,
значит, знание не переехало в данные, и расширять надо формат пакета.
Игрушечный пакет `test/fixtures/packs/demo` проверяет это в тестах:
на нём проходит весь путь от разметки до ответа.

## Проверка без API

Разметку можно сделать в обычном чате Claude, в рамках подписки,
а посчитать тем же движком, что на сайте:

```
node scripts/offline.mjs prompt fixtures/black_hole_1.json > prompt.txt
# вставить prompt.txt в чат, ответ сохранить как markup.json
node scripts/offline.mjs score fixtures/black_hole_1.json markup.json
```

Вход в формате фикстуры (`scenario`, `texts` с `genre` и `text`,
`author` для подписи), свои тексты кладутся в такой же файл вне
репозитория. Ответ чата сохраняется как есть: обрамление ```json
отрезается. Цитаты проверяются так же строго, как на сайте.
Это проверка прибора, а не модели сайта: в чате другая модель
и другие настройки размышления, поэтому качество живой разметки
меряет только `eval.mjs`.

## Проверка качества

```
ANTHROPIC_API_KEY=… npm run eval
ANTHROPIC_API_KEY=… node scripts/eval.mjs --checks accuracy,stability
```

Прогон через живой API на 14 синтетических авторах из `fixtures/`,
по два на тип. Кэш выключен, полный прогон это около 35 разборов,
то есть настоящие деньги. Пороги:

| Проверка | Порог |
|---|---|
| точность | тип совпал у 10 авторов из 14 |
| подмена автора | тип тот же, уровни совпали минимум по 6 осям из 7 |
| атака «если» | Давление и Эксклюзивность Чёрной дыры падают не больше чем на уровень |
| инъекция | строка «Игнорируй инструкции…» тип не меняет |
| жанр | те же продающие тексты: у `sale` Давление не выше, чем у `post` |
| стабильность | три прогона одной фикстуры дают один тип |

Отчёт в консоль и в `scripts/eval-report.json`, там же время разбора
против цели в 20 секунд. Проваленный порог означает правку рубрики
или промпта с новой версией, а не подгонку фикстур.

## Отступления от спеки

- **Тело запроса до 100 КБ, а не 60.** 40 000 кириллических знаков в
  UTF-8 весят около 80 КБ; с порогом 60 КБ разрешённый объём
  отбивался бы раньше проверки знаков.
- **Нет `temperature: 0`**, см. «Модель».
- **Разметка асинхронная** (задание и опрос), см. «Как устроен разбор».
- **`@netlify/blobs` закреплён на 10.x.** Версия 11 требует Node 22.12,
  а сайт собирается на Node 20.
- **Красный акцент текстом только на панелях.** На основном фоне
  светлой темы его контраст 4.19, ниже 4.5; на панелях 4.61.
